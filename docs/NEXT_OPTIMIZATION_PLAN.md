## 2. 下一阶段六大可落地优化方向（`v71+`）

### 方向 A：精确稀疏工作表 + 边描述符 SoA 分离 + 候选边剪枝（预计 `-60 ~ -100 s`）
- **对应瓶颈**：`R3–5` CPU `p1`（总 `p1=231.80 s`）与 `R6–52` GPU/CPU `p3`（总 `p3=309.42 s`），对齐 PPT Slide 12（`43.98%` 候选边预剪枝）与 Slide 21 规划 2。
- **核心切入点**：`src/cpp/fides_cpu.cpp`、`src/cpp/fides_gpu.cu`。
- **改造思路**：
  1. 将 `92.5M` 节点 / `391.5M` 边拓扑中的只读几何属性、走廊成员索引与高频更新热数据（`occ`、`hist`、`presentCost`）按 SoA 分离重组，减少高扇出连续扩展时的缓存行与 HBM2 浪费；
  2. 为 `R6–52` 活跃拥塞集维护紧凑的稀疏边/节点工作表（仅加载活跃盒子/走廊内的热邻接偏移），避免每次查询都穿透全图大数组；
  3. 结合方向/SLR/边界不可达剪枝，直接跳过明显偏离目标门区或必破包络的候选扩展边，降低无效 pop 次数（`v70` 总 pops `270.2 亿`）。

### 方向 B：`R3–5` 高扇出无冲突子集多卡协同卸载（预计 `-40 ~ -70 s`）
- **对应瓶颈**：`R3–5 = 129.98 s`（占整个 `Routing` 近 20%）。
- **历史教训护栏**：`v35` 已实证把 `R3–5` 全轮 `Pass 1` 无区分送入 `Tier-A` 会引发 `R4/R5 +25–34%` 过载级联；因此绝不整轮一刀切下发 `Tier-A`。
- **改造思路**：
  1. 在 `R3–5` 中保留顺序敏感的高扇出主干在 `36` 核 CPU 精确提交，但对通过**空间不相交预筛（无共享源/无净空交叉）的 `Pass 1/Pass 2` 中等包围盒批次**分片卸载给 `4×V100` `Tier-B1` 并行探测；
  2. 严格限制批内冲突率阈值，发现过载回退苗头即动态收缩卸载批尺寸。

### 方向 C：`R6–52` 按前沿宽度/显存自适配多卡 GPU Lane 与 `P3` 动态阈值（预计 `-25 ~ -45 s`）
- **对应瓶颈**：`R6–52 = 327.49 s`（当前 `v70` 统计 `wide_ok=4, ov=126, gpu_fb=77`），对齐 PPT Slide 21 规划 3。
- **改造思路**：
  1. 优化 `4×V100` `LPT` 按 Net/工作量预估分片（考虑 `lastPops` 与 `netSize` 加权，而非仅固定数量切分），消除少数超级大 Net 落入单张 V100 造成其余 3 卡同步栅栏空等；
  2. 压低 `gpu_fb=77`：在 GPU 端发现盒内重试无效时更快按预算提前让渡给精准边界退避策略，而不是耗尽 `256k/512k` 预算再回落 CPU；
  3. 对 `R18–45`（`active ≈ 200–1,500`）评估小规模多流并行 `Pass 3`，减少核启动与空闲等待。

### 方向 D：`RWRoute.preprocess`（`19.54 s`）并行化与 `attach` 进一步隐藏（预计 `-15 ~ -25 s`）
- **对应瓶颈**：`F4_V67_PREPROC rwPre=19.54 s` + `FIDES_V67_NATIVE_ATTACH=4.52 s`（合计 `24.06 s`）。
- **改造思路**：
  1. 剖析 `RWRoute.preprocess`（`v67_patch.py` / `PartialRouter.java`）：将其内部的 `DesignTools.makePhysNetNamesConsistent`、`createPossiblePinsToStaticNets`、`createMissingSitePinInsts` 拆解并按无共享写冲突粒度的 Net 分片在 `36` 核 `ForkJoinPool` 并行；
  2. 将 `FIDES_V67_NATIVE_ATTACH` 中的 `slr.i32le` 与静态掩码预打包合并进 `PRELOAD`，`attach` 时仅传轻量的动态 `occ/hist/pcc`，把 `Preproc + Init` 总墙钟压缩到 `< 25 s`。

### 方向 E：后处理 `Post + SetPIPs + Materialize + Pins` 深度流水与脏网更新（预计 `-18 ~ -28 s`）
- **对应瓶颈**：`materialize=13.69 s` + `F4_V66_POST=11.49 s` + `SETPIPS=7.52 s` + `CHECKPIPS=1.31 s` + `STATS_WL=3.97 s` + `pins=3.84 s` ≈ `41.8 s`。
- **改造思路**：
  1. **脏网增量 `updatePinsIsRouted`**：`setPIPsOfNets` 仅修改了实际改道的 Net，直接记录脏 Net 掩码并跳过已保留的干净 Net，把 `pins=3.84 s` 压到 `< 0.5 s`；
  2. **`STATS_WL (3.97 s)` 移入写出并发区**：与 `writeCheckpoint` 及 `64` 分片 `F4_V66_INPROC_DCP_CHECK` 同时运行，完全藏进 `15.4 s` 写盘期间；
  3. **流水化 `Materialize` 与 `POST`**：在末轮收敛确认的同时流式导出 `connPaths -> Java RouteNode` 绑定表，减少 `13.69 s` 串行阻塞。

### 方向 F：微尾 `R56–58`（`40.53 s`）精确 2-hop 小邻域让路（预计 `-20 ~ -30 s`）
- **对应瓶颈**：`v70` `R56–58` 仍耗 `40.53 s`（`R56 over=8, fb=2, 12.63 s`；`R57 over=5, fb=1, 13.86 s`；`R58 over=1, fb=1, 14.04 s`），而 `R59–64` 仅耗时 `17.75 s`。
- **历史教训护栏**：`v69` 实锤证实 `microDeepNbr`（`192` 大范围拆邻居）会引爆 `over=1→4/5` 三连震荡；`v64/v65` 证实缩短首探针 `2M/24` 到 `500k` 会引爆 `fb=3..5`；`v68` 证实不可对 `over>=3 / act>=5` 并发放行 `0/-1`。
- **安全改进思路**：
  1. 在 `R55+` 对连续失败连接（`fs >= 1`）不全局扩拆 `192` 条大邻居，而仅做**精确路径交叉检测**：只临时拆掉直接占用 `fs>=1` 连线候选出口关键节点的 `1–4` 条超小跳数邻居，消除盲拆震荡风险；
  2. 保持 `R58+ over<=1 && act<=2` 的无界单线门控与 `microStuck (6×/12×)`，让 `R53–64` 有望再压缩至 `30 s` 以内。
